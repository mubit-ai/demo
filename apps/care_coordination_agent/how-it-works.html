Care Coordination Agent

A bounded LLM agent coordinates one synthetic patient's care encounters. Across fresh process restarts it learns patient-specific operational strategies from observed outcomes and one clinician correction — while current chart instructions always outrank historical memory.

Pathway: deterministic (harness-owned SDK calls) Mubit: remember · recall · record_outcome All patients, charts & clinicians are synthetic

1 · The scenario

The agent works through validated structured actions inside a deterministic encounter simulator with an 8-action budget: outreach → explain_instructions → check_understanding → arrange_transportation → book_follow_up → close_encounter (or escalate). The simulator hides patient-specific ground truth the agent must discover:

T1 · Contact

SMS gets no reply; calls before 17:00 hit voicemail; a call at ≥17:00 establishes contact. Deliberately not a universal "SMS never works" rule.

T2 · Communication

Generic label-style explanations never establish understanding. A failed comprehension check triggers a scripted clinician correction adding approved wording to the chart; only that text plus a check confirms understanding.

T3 · Coordination

Booking before transportation is arranged fails. Transport first, then booking, succeeds.

2 · How the agent and Mubit are wired

Two guarantees are structural, not prompt-level: every SDK call happens at a fixed code point in the harness, and lesson text can only be produced by lessons.py from evidence that actually occurred. The runtime model chooses actions — it cannot author memory.

3 · The learning loop, step by step

owned by: harness

Capture

The agent acts; the simulator returns observed outcomes (SMS no_response, failed comprehension check, unsuccessful booking…). Only what the agent was allowed to see can become evidence.
owned by: code

Distill

lessons.py derives a candidate only if the full evidence pattern occurred — e.g. a contact lesson requires SMS no-reply followed by a successful call. Guidance stays conditional: "when no newer contact preference is available…", never "SMS never works".
owned by: code

Gate

The candidate is persisted only if it re-derives identically from the finished encounter, provenance matches, and it contains no treatment-like language and no hidden-simulator markers. Anything else is dropped.
owned by: Mubit

Promote

remember(intent="lesson", upsert_key=version:experiment:patient:category) — idempotent per patient+category, run-scoped. Re-teaching updates the slot instead of duplicating.
owned by: harness

Inject

One recall before action 1, re-validated against the Lesson schema; the list is frozen and SHA-256-hashed for the whole execution. Prompt policy fixes authority: current chart → current observations → recalled lessons.
owned by: Mubit

Attribute

After the encounter, record_outcome reinforces exactly the lessons the agent cited — success raises their evidence counters; failure decays them.

4 · Example data at each step

Real field values from the code and scenarios (patient SYNTH-PT-0042, channels sms|phone_call, chart slots 2026-10-21T09:00…). Every lesson becomes a hypervector in the medium; recall is the SDM consensus read over it.

① Capture — agent decision in, simulator outcome out (teaching encounter T1): 
// agent → simulator (pydantic-validated structured decision)
{"action": "outreach", "arguments": {"channel": "sms", "local_time": "09:00"},
 "rationale": "Chart lists sms and phone_call; try the lighter channel first.",
 "recalled_lesson_ids": []}
// simulator → observed outcome (the only ground truth the agent ever sees)
{"action": "outreach", "channel": "sms", "local_time": "09:00", "status": "no_response"}
② Distill — what lessons.py derives from that evidence (and only if the full pattern occurred: SMS no-reply followed by a successful call at ≥17:00): 
{"category": "contact_strategy", "patient_id": "SYNTH-PT-0042",
 "applicability": "when no newer contact preference is available for this patient",
 "guidance": "SMS receives no reply; a phone call at 17:00 or later establishes contact",
 "evidence_type": "observed_outcome",
 "evidence_summary": "T1: outreach(sms,09:00)→no_response; outreach(phone_call,17:05)→contact"}
③ Gate — a candidate is persisted only if it re-derives identically from the finished encounter, provenance matches, and it carries no treatment-like language and no hidden-simulator markers. Dropped example: a draft saying "switch the evening dose" — medication wording — never reaches Mubit.
④ Promote — the write, idempotent per patient + category: 
client.remember(
  content = "[experiment:cc-x] [demo:cc-memory-1]\n" + json.dumps({…lesson, experiment_id, source_encounter_id…}),
  intent="lesson", lesson_type="failure",          // learned from a failed SMS, not a correction
  lesson_scope="run", lesson_importance="high", agent_id="care-coordination-agent",
  upsert_key="cc-memory-1:cc-x:SYNTH-PT-0042:contact_strategy",   // re-teaching updates this slot
  wait=True)
⑤ Inject — recall before action 1; only prompt-safe fields survive validation, and the list is frozen and hashed for the whole execution: 
// in: recall(query="care coordination operational lessons for synthetic patient SYNTH-PT-0042",
//          entry_types=["lesson"], evidence_only=True)
// out: entry {"id": "5d3f…", "content": "[experiment:cc-x] [demo:cc-memory-1]\n{…}"}
// → after strict re-validation, the frozen snapshot the model receives:
[{"id": "5d3f…", "category": "contact_strategy", "applicability": "…",
  "guidance": "…", "evidence_summary": "…"}]      // snapshot SHA-256 identical across all three arms
⑥ Attribute — after the encounter, only cited lessons are reinforced: 
memory.record(reference_id="5d3f…", succeeded=True,
              rationale="E1: contact established on first call after 17:00")
// → client.record_outcome(reference_id="5d3f…", outcome="success", signal=1.0,
//                         verified_in_production=False)

And in E2, the same store must lose: chart says "morning calls 09:00–11:00", the stored lesson says "call ≥17:00" — the agent calls at 09:30 and the run scores PASS on current instruction winning.

Recall is strict: entries failing the marker, experiment, patient, category or schema checks are dropped before the model ever sees them. Reference IDs shown in the UI come only from real Mubit recalls — none are ever fabricated.

5 · What gets measured

E1 — three-arm controlled comparison (fresh processes, frozen snapshot)

ArmMemoryWhat it isolates
no_memoryemptycold agent behavior
full_memorythe exact frozen, hashed snapshotwhat the learned lessons change
ablated_contactcontact lessons removed, others intactper-category causal attribution — removing one lesson type must reverse exactly the behaviors it drove

Scoring is deterministic (completion, comprehension, premature booking, transport-confirmed booking, efficiency…) — no LLM judge. Zero Mubit writes during evaluation.

E2 — current-preference override

The chart now says "morning calls, 09:00–11:00", contradicting the stored after-17:00 lesson. The simulator rewards only the current instruction, and the run reports a hard PASS/FAIL on the memory system not overriding current truth. Memory is operational guidance, never a second chart.

6 · What this demonstrates (the indirect answers)

deterministic pathway

Mubit calls at fixed code points; memory content is auditable by reading code. The right shape when lessons are compliance-grade.

over-indexing control

Lessons are conditional by construction, E2 proves current truth wins, and ablation shows influence is measured by behavior change — not by citations.

durable cross-run learning

Lessons survive process restarts — Mubit is the only memory; local trace files are audit artifacts. Fresh executions behave differently because of what was learned.

influence attribution

Reinforcement touches only cited lessons; the ablation arm proves the causal story per category.
