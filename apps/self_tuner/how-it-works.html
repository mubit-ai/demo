Self-Tuner

The system prompt is a versioned, server-side resource. A fixed deterministic executor runs the ACTIVE prompt's rules, so any accuracy change between versions comes from the prompt, not from model variance. Outcomes accrue; reflect distills lessons from failures; the optimizer proposes a challenger; an A/B on held-out data decides activation.

Measured: champion v1 answers 3 of 4 held-out emails. The challenger — generated by the server from the lessons — answers 4 of 4, and is activated.

2 · Loop

Champion

v1 is stored and activated server-side. Training emails run through the deterministic executor. Outcomes record against the entries.

Loop-safety → guardrail

The double-probe failure shape is detected. A rule entry is written — rules always inject first.

Reflect + optimize

reflect() distills the failures into lessons. optimize_prompt() generates a challenger from them, server-side. It is NOT auto-activated.

A/B, then activate

Both versions execute on held-out data. Champion 3/4. Challenger 4/4 — it added the missing refund rule. The challenger is activated. On a loss, the champion stays.

Procedural memory

The escalation procedure is stored as a server-side playbook and fetched at run time.
