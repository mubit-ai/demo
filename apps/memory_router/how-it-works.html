Memory-Augmented Router

A keyword router delegates support requests to 3 fictional specialists. The router sends the wrong specialist first on half of the held-out requests. The agent stores raw facts and per-step outcomes only. Mubit reflects, gates, and decides which lessons exist. Mubit also decides what is discarded and what is recalled in the next run.

Recorded live result: first-route accuracy 50% → 83.3%. Handoffs 3 → 1.

Pathway B: Mubit-decided lessons Pathway C: model-mediated tool calls (--mode tools) remember(fact) · record_step_outcome · reflect · recall All requests and specialists are fictional

2 · Three integration pathways in one app

A · deterministic

The harness calls the SDK at fixed points

The harness recalls before the decision. The harness records outcomes after the decision. Lesson content is authored outside the model. Used by the sibling apps (care coordination, supply chain).

B · Mubit-decided

The agent stores evidence. Mubit writes the lessons.

The agent never writes a lesson. The agent stores raw observed attempts (remember(intent="fact")) and 1 outcome per step (record_step_outcome). Mubit's reflect() proposes lessons on the server. The validation gate accepts a candidate at a score of 0.6 or more. The gate rejects a candidate at 0.25 or less. Rejected entries return marked is_stale. Recall filters stale entries before the model sees them. This is the default mode.

C · model-mediated tools

The model calls mubit_recall itself

With --mode tools, the harness calls nothing. The router model invokes Mubit recall as a function tool. The model decides whether to consult memory. The model chooses the query. The model may call the tool at most 2 times. Any baseline override must cite lesson IDs that the tool returned. Otherwise the run fails.

3 · The teaching loop

owned by: harness instrumentation

Capture

After each attempt, the app stores the observed facts as they happened: remember(content="Observed fictional routing attempt: …", intent="fact"). The write path writes no preferred route, no rule, and no hindsight directive. The write path cannot editorialize.
owned by: Mubit reflect

Distill

One call runs: advanced.reflect(include_step_outcomes=True). Mubit's server-side model reads the evidence stream, including the per-step rewards. Mubit proposes structured lessons. The app never prompts for lessons.
owned by: Mubit's validation gate

Gate

The gate scores each candidate. A score of 0.6 or more makes the lesson active. A score of 0.25 or less rejects the lesson and marks it stale. A score between the two keeps the lesson pending until outcome evidence arrives. After 3 outcomes, the realized success rate re-runs the gate. Trust is losable. Recall filters is_stale entries, non-lesson types, and entries from other runs.
owned by: Mubit scope rules

Promote

Lessons that keep earning outcomes climb the scope ladder: run → session → global. This demo keeps lessons run-scoped to the experiment. Promotion is server policy, not app code.
owned by: harness, or the model in tools mode

Inject

Preload mode: the harness recalls with the routing query and supplies the lessons. Tools mode: the model calls mubit_recall and selects the query. The model may skip the call when the baseline is clearly correct.
owned by: Mubit counters

Attribute

Two levels apply. record_outcome reinforces cited lessons only. A lesson that was not used cannot gain credit. record_step_outcome records 1 signal per step with signal=±1.0. The committed teach trace shows the pattern [-1, +1] × 3: a wrong first route, then a resolution by handoff, for all 3 teaching cases.
