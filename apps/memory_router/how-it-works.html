Memory-Augmented Router

A keyword-baseline router delegates support requests to three fictional specialists, and keeps getting the wrong specialist first. The agent stores only raw evidence and per-step outcomes — Mubit itself reflects, gates, and decides which lessons exist, which are discarded, and what gets recalled into future runs.

Pathway B: Mubit-decided lessons Pathway C: model-mediated tool calls (--mode tools) remember(fact) · record_step_outcome · reflect · recall All requests & specialists are fictional

1 · The scenario

A regex baseline routes by keywords: api|endpoint → technical, invoice|receipt → billing, else account. It is wrong in both directions on the held-out set — requests that need meaning-level reading, not keyword matching:

The teaching set (T1–T3) is three requests like H1–H3. The learned lessons must transfer across paraphrases (H-cases) without capturing the negative controls (C-cases) — C2 shares the word "invoice" with a billing-context lesson, so naive similarity is actively misleading here.

2 · The three Mubit integration pathways — one app, switchable

A · deterministic

Harness calls the SDK at fixed points

The harness recalls before the decision, passes lessons into the prompt, and records outcomes after. Lesson content is authored outside the model. Used by the sibling apps (care coordination, supply chain). Best when lessons are compliance-grade and auditable by inspection.

B · Mubit-decided

The agent stores evidence; Mubit writes the lessons

The agent never authors a lesson. It stores raw observed attempts (remember(intent="fact")) and one outcome per step (record_step_outcome). Mubit's reflect() extracts lesson candidates server-side and the validation gate (accept ≥ 0.6, reject ≤ 0.25, revalidation from realized success rates) decides what becomes a lesson, what stays pending, and what is discarded — rejected entries return marked is_stale and are filtered at recall. This is the default mode here.

C · model-mediated tools

The model itself calls mubit_recall

With --mode tools, the harness calls nothing. The router model invokes Mubit recall as a function tool — deciding whether to consult memory at all (skipping is allowed and correct for C1–C3), what query to use, and how often (capped at 2). Grounding is enforced in code: any baseline override must cite lesson IDs the tool actually returned, or the run fails. New in this branch.

3 · The teaching loop — who decides what

owned by: harness instrumentation

Capture

After each routing attempt, the observed facts are stored exactly as they happened: remember(content="Observed fictional routing attempt: …", intent="fact"). No preferred route, rule, or hindsight directive is written anywhere — the write path physically cannot editorialize.
owned by: Mubit reflect

Distill

One call — advanced.reflect(include_step_outcomes=True) — has Mubit's server-side LLM read the evidence stream (including the per-step rewards) and propose structured lessons. The agent app never prompts for lessons itself.
owned by: Mubit's validation gate

Gate

Candidates are scored: ≥ 0.6 → active, ≤ 0.25 → rejected and marked stale, between → pending until outcome evidence arrives. Once ≥ 3 outcomes accumulate, realized success rate re-runs the gate — trust is losable. Recall filters is_stale, non-lesson types, and wrong-run entries before the model sees anything.
owned by: Mubit scope rules

Promote

Lessons that keep earning outcomes climb the scope ladder (run → session → global); here the demo keeps them run-scoped to the experiment, and promotion is server policy, not app code.
owned by: harness (or the model, in tools mode)

Inject

Preload mode: harness recalls with the routing query and supplies lessons. Tools mode: the model invokes mubit_recall itself, choosing the query — and may skip it when the baseline is clearly right.
owned by: Mubit counters

Attribute

Two granularities: record_outcome on cited lessons (a lesson that wasn't used can't be reinforced), and record_step_outcome per step with signal=±1.0 — the committed teach trace shows the honest pattern [-1, +1] × 3: wrong first route, resolved after handoff, for every teaching case.

5 · What this demonstrates (the indirect answers)

Mubit-decided memory

What to store, what to discard, and what to recall are decided by Mubit's reflect + validation gate from raw evidence and step outcomes — not by hand-written rules or free-form LLM writes.

pattern transfer without capture

Lessons generalize across paraphrases (H1, H3) while keyword-adjacent negative controls (C2) stay on baseline — conditions and scoping survive the round trip through memory.

grounded overrides only

In every mode, an override must cite lesson IDs that actually came back; invented citations fail the run. Filtered recall (is_stale, type, scope) means discarded knowledge never reaches the model.

tool-mediated memory

--mode tools shows the third integration shape: the model spends a tool call on memory only when it judges it useful — selective recall at decision time, with identical grounding rules.
